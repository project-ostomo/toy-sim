# Directory appearance audit

Audited 2026-09-24 by visually viewing all seven Figma references at 1600×900 and the matching software gallery images. Charon is an intentional font choice. This report concerns composition and visible presentation; it does not require copying Figma's layer structure.

Figma file: `kvxDvZDyEbkfgU25IDzyyd`.

## Highest priority findings

1. **The gallery does not verify the designed screens.** Every society fixture calls `society::draw` directly on the root UI, and the standing fixture calls `standing_card` directly. See `crates/osg-client/src/ui/shell/tests.rs:449`. Consequently the images omit the surrounding shell, floating window position, window background, border, title bar, interior margin, selected-contact pane and Overview. The Figma Directory is about 940×740, typically positioned at x358/y70; its sidebar is about 274px and its content area about 625px. The images fill a 1600×900 black canvas. These are component captures, and cannot establish full-screen parity. The black background difference partly comes from this fixture framing; it must not all be attributed to the runtime theme.
2. **The actual Directory navigation and content composition differ substantially.** `society.rs:122` builds an account header and global horizontal tabs, then `directory_panel` at line464 uses two equal columns. Figma has a persistent narrow hierarchy sidebar with four affiliation shortcuts, search and a tree grouped by blocs; selected principal identity and contextual tabs occupy the wider right pane. `politics.rs:102` opens a separate generic diplomacy editor, removing the tree. This structural change accounts for far more of the mismatch than typography.
3. **The principal screens largely expose forms instead of the specified summaries.** Publishing and agreement creation controls dominate the current pages; the reference presents published records, status, provenance and compact actions. Rebuild the visible summaries and open creation/editing controls from their relevant actions.
4. **Rows, cards and statuses lack their intended visual hierarchy.** Figma uses alternating navy row fills, aligned columns, compact outlined badges, cyan active-tab underlines, muted small uppercase section labels, amber pending/disputed states and red war banners. The current pages mostly consist of unframed labels, separators and solid blue selected buttons. Restoring those surfaces and semantic accents will recover much of the missing color and information density.

## Scale, spacing and compact checks

Figma uses approximately 12–14px body text and 20–22px identity headings, with short row heights and secondary text around11–12px. Charon can retain that scale. The main problem is the lack of hierarchy and framing, rather than the intentional font family. Current repeated global headings and large form controls displace useful records, while most of the desktop canvas remains empty.

Visually checked compact images: `target/ui-gallery/society-polity-900x650.png`, `society-bloc-inbox-900x650.png`, `society-sources-900x650.png`, and `society-standing-900x650.png`. The polity detail starts at x456, and the explanatory text is clipped at the right edge. The fixed equal columns leave too little space for details. The compact images also retain the global horizontal tabs, even though those consume space that the Figma sidebar/contextual tabs would distribute differently. Standing remains four lines on an otherwise empty canvas. A rectangle-bound assertion alone does not detect text clipping or missing composition.

## Recommended correction order

1. Add complete shell captures with representative populated records, matched selected principal, matched window size, request states and permissions. Include organization Members and hostile contact card scenarios explicitly. Keep component screenshots separately identified.
2. Implement the persistent Directory sidebar, principal header and contextual tabs; use a bounded sidebar width and allocate the remaining width to detail. Choose a compact layout that preserves readable details.
3. Build polity overview, publication summaries, agreements and officer requests as tables/cards with semantic badges. Move creation forms behind the matching actions.
4. Build the trust matrix, organization member table and composed contact card.
5. Compare complete captures again for row spacing, title scale, dark navy surfaces, cyan selection and amber/red/green states. Preserve the requested Charon/Sarasa fonts and ordinary headless-client officer behavior.

## Implementation follow-up

The Directory now uses a persistent sidebar, identity header, contextual tabs, a bounded detail scroll area, and navy table/card surfaces in `crates/osg-client/src/ui/shell/society/presentation.rs`. Polity summaries show actual posture and recognition records. Withdrawal banners and officer request cards use the new request/cancel/grant/refuse RPC workflow. Declaration and agreement editors open from collapsed actions; published records have revision controls, semantic category/term/status badges, and public notes. Trust sources have a category matrix and an expandable priority editor. Organization Members is a populated fixture at `target/ui-gallery/society-organizations-1600x900.png`.

The contact card is composed by `society::contact_card` and opens from **Show affiliation** in the selected-item pane. It includes IFF lineage, political posture, standing provenance, published list status, personal overrides and Directory navigation; its surrounding popup also supplies ship identity/range and Look at. Its gallery fixture now uses a hostile contact and a card-sized window within the shell.

The gallery harness uses the real desktop framing. Directory fixtures include ambient contacts, a pending withdrawal, an application, multiple published categories, six organization members and hostile posture. The first visual review confirmed the desktop composition and colored cards now follow the reference. Its geometry check caught an 11px standing-card overflow; the body now uses a bounded scroll area for shorter windows.

The model has no founding dates, membership dates, declaration publication dates, geographic jurisdiction targets, or published officer-policy metadata. These fields are not fabricated in the UI. Automated officers remain ordinary accounts operated through headless clients.
